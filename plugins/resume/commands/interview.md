# resume:interview

## 역할
멘티의 경력/프로젝트를 인터뷰합니다. 52세션 패턴 기반 질문 프레임 + 5why 드릴다운으로 Why·근거·수치·기술 진위를 캐냅니다.
결과를 `wiki/projects/*.md`, `wiki/skills/*.md` 에 누적 저장합니다.

---

## 사전 고지 (인터뷰 시작 시 반드시 출력)

```
인터뷰를 시작합니다.

진행 방식:
- 프로젝트별로 질문합니다. 하나씩 집중해서 답해주세요.
- 답변이 모호하면 꼬리질문이 이어집니다 (보통 항목당 3~7개).
- 8질문마다 자동 저장됩니다. 언제든 중단하고 나중에 재개할 수 있습니다.
- "모르겠다"는 답은 괜찮습니다. 모르는 게 부끄러운 게 아니라,
  거짓 수치가 면접에서 무너지는 게 더 위험합니다.
- 시작 전 질문 있으면 해주세요.
```

---

## 실행 절차

### 1단계: vault 및 세션 확인

`scripts/resolve-vault-root.sh <id>` 로 MENTEE_ROOT 확인.

`.resume-session` 읽기. `pipeline_stage` 가 `init` 이면:
```
init은 완료됐습니다. /resume:assess {id} 를 실행하세요.
```
`pipeline_stage` 가 `assess` 이면:
```
아직 assess가 완료되지 않았습니다.
/resume:assess {id} 를 먼저 실행하세요.
```
(`pipeline_stage` 허용 값: `interview`, `star-sbi`, `export`. `init`/`assess`이면 중단.)

`assess_level` 읽기. `dig_state` 읽어 재개 여부 판단:
- `questions_asked > 0` 이고 `current_project_id` 가 있으면: "이전 세션이 있습니다. {current_project_id} 부터 재개할까요? (Y/N)"

### 2단계: 프로젝트 순서 결정

`wiki/projects/` 를 Bash로 목록화.

우선순위:
1. L1이면 최근 경력 프로젝트 먼저 (frontmatter `period` 기준 최신 순)
2. L0이면 빈 템플릿(project-1)부터
3. L2/L3이면 `assess_flags` 가 많은 프로젝트 먼저

`projects_completed` 에 있는 프로젝트는 건너뜀.

### 3단계: 프로젝트별 인터뷰

각 프로젝트에 대해 다음 흐름으로 진행.

#### 3-1: 도입 질문 (1~2개)

프로젝트 요약을 보여주고 확인:
```
[{프로젝트명}] 을 살펴보겠습니다.

이력서에는 이렇게 적혀 있는데요:
"{원문 요약}"

우선 한 문장으로: 이 프로젝트에서 당신이 한 핵심은 무엇인가요?
(결론부터 말해주세요)
```

L0 빈 템플릿이면:
```
첫 번째 프로젝트/경험을 하나 골라봅시다.
기억에 남는 것, 자신 있는 것, 아무거나 괜찮습니다.
프로젝트명과 기간, 역할을 간단히 소개해주세요.
```

#### 3-2: 52세션 질문 프레임 적용 (핵심)

아래 결핍 패턴을 항목의 `assess_flags` 와 실제 답변을 보며 순서대로 적용한다.
**플래그가 없는 항목도 기본 1~2개는 확인한다.**

---

**[Why부재 — 51% 빈도]** `assess_flags` 에 Why부재가 있거나 답변에서 이유가 없을 때:
```
왜 이 기술/방식/결정을 선택했나요?
당시 어떤 문제 상황이 있었고, 다른 선택지는 무엇이었나요?
```

**[AI 미활용 확인 — 45% 빈도]** 개발/데이터 관련 프로젝트 시 의무 질문:
```
이 작업에 AI 도구(ChatGPT, Copilot 등)를 활용했나요?
활용했다면 어떻게? 안 했다면 이유가 있나요?
```

**[수치 과잉 — 43% 빈도]** 이력서에 퍼센트/배수/시간 수치가 있을 때:
```
"{수치}" — 이 숫자는 어떻게 측정했나요?
부하 조건, 측정 도구, 비교 기준은 무엇인가요?
(맥락 없는 수치는 면접에서 오히려 독이 됩니다)
```

**[두괄식 미적용 — 39% 빈도]** 답변이 배경부터 길게 시작할 때:
```
잠깐, 결론부터 해주세요.
한 문장으로: 이 경험의 핵심 기여는 무엇인가요?
```

**[기초 CS 부족 — 39% 빈도]** 핵심 기술 스택이 언급될 때:
```
{기술명}의 동작 원리를 설명해줄 수 있나요?
```
답변 수준을 4단계로 분류: 아는것(개념만) / 해본것(사용 경험) / 설명가능(원리 설명) / 최적화경험(튜닝/트러블슈팅).
`wiki/skills/{기술명}.md` 에 레벨 기록.

---

#### 3-3: 5why 드릴다운

각 답변에 대해 충분히 구체화될 때까지 꼬리질문:

```
Why 구체화 → 대안 비교(How) → 실제 측정/검증(해본 것 vs 아는 것) → 트레이드오프
```

답변이 구체적이면 다음 항목으로. 모호하면:
- "조금 더 구체적으로: {모호한 부분}은 어떻게 됐나요?"
- "그 결정에서 포기한 것은 무엇이었나요?"
- "그 숫자(또는 결과)를 지금 다시 보면 어떻게 달라질 것 같나요?"

#### 3-4: 실력 진위 의무질문 (매 프로젝트 1회)

```
이 프로젝트에서 방금 얘기한 결정들 — 직접 내린 결정인가요,
아니면 팀 전체가 이미 쓰던 방식인가요?
```

- 직접 결정이 아닌 것으로 확인되면: `assess_flags` 에 `실력진위불명` 추가. star-sbi에서 `> 추정:` 마커 사용 예정 기록.

#### 3-5: 빈약 항목 강제 발굴

`assess_flags` 에 `빈약` 이 있거나 답변이 1~2문장에 그칠 때 1회 강제 시도:
```
이 부분이 짧게 적혀 있는데, 혹시 더 있는 것 아닌가요?
잘 안 드러난 기여나 기억나는 에피소드가 있으면 꺼내봅시다.
```

#### 3-6: 심리 완충

수치 부풀림이나 잘못된 정보 발각 시:
```
모르는 게 부끄러운 게 아닙니다. 거짓 수치가 면접에서 무너지는 게 더 위험해요.
솔직하게 "당시엔 그렇게 생각했는데 지금 보면 과했다"도 좋은 답변입니다.
```

### 4단계: checkpoint (8질문마다)

누적 `questions_asked` 가 8의 배수가 될 때마다:

1. `.resume-session` 업데이트:
   ```yaml
   dig_state.questions_asked: {N}
   dig_state.last_checkpoint: {N/8}
   dig_state.current_project_id: "{현재 프로젝트 id}"
   last_updated: YYYY-MM-DD
   ```
2. 현재까지 파악한 내용을 `wiki/projects/{project-id}.md` 에 append:
   ```
   ### 업데이트 ({날짜}): 인터뷰 checkpoint {N/8}
   [수집된 내용]
   ```
3. 출력:
   ```
   저장됨 (checkpoint {N/8}). 여기서 중단하고 나중에 재개할 수 있습니다.
   계속하려면 그냥 답변해주세요.
   ```

### 5단계: escalate 판정

다음 중 하나라도 해당하면 escalate:

| 조건 | 판단 |
|------|------|
| 동일 항목에서 3회 이상 "모르겠다" / "기억 안 난다" | escalate 후보 |
| 실력 진위 불명 항목이 전체 프로젝트의 50% 초과 | escalate 후보 |
| 핵심 기술 수준이 L2(해본것) 미만이고 이력서에 핵심으로 기재 | escalate 후보 |

escalate 후보 발생 시 인터뷰 완료 후 다음 출력:
```
몇 가지 항목은 1:1 세션에서 더 깊이 다루면 좋겠습니다.
escalate-handoff.md 를 생성합니다. william과의 심화 세션 준비 파일입니다.
```

`escalate-handoff.md` 생성 내용:
```markdown
---
mentee_id: "{id}"
created: {날짜}
escalate_reason: []   # 위 조건 중 해당 항목
---

# escalate 핸드오프: {id}

## 인터뷰 요약
[세션 요약]

## escalate 이유
[구체적 이유]

## william 심화 세션 권장 항목
[항목 목록]

## 멘티 상태 (인터뷰 중 관찰)
[관찰된 심리적 패턴, 방어적 태도 등]
```

`.resume-session.escalated: true` 로 업데이트.

### 6단계: 완료 처리

모든 프로젝트 인터뷰 완료 시:

- `dig_state.projects_completed` 업데이트
- `pipeline_stage: star-sbi` 으로 업데이트
- `wiki/projects/*.md` 최종 append

출력:
```
인터뷰 완료. {N}개 프로젝트, 총 {M}개 질문.

다음: /resume:star-sbi {id}
```

escalate 후 계속하는 경우:
- `/resume:interview {id}` 재실행 (인터뷰 심화 세션 후 재개)
- 또는 `escalate-handoff.md` 를 멘토에게 전달한 후 `/resume:star-sbi {id}` 직접 실행

---

## wiki 누적 규칙

- 기존 페이지 있으면: 섹션 단위 append + `### 업데이트 (날짜):` 표기. 덮어쓰지 않음.
- 신규 기술 언급 시: `wiki/skills/{기술명}.md` 생성. frontmatter에 `level`, `evidence_flags` 포함.
- LLM 추정/해석은 `> 추정:` 마커 필수.
- 직접 안 내린 결정: `> 추정:` 마커 + `실력진위불명` 플래그.

> 구체 예시: `examples/sample-vault/wiki/projects/fintech-startup.md`, `wiki/skills/redis.md` — 인터뷰 정제 결과·기술 레벨 기록 방식 참조.
