# 상품조회 API Redis 캐시 최적화

## 요약
핀테크 스타트업 A사에서 상품조회 API의 극단적 응답 지연(P99 18~20초) 문제를 Redis
Look-aside 캐시 도입으로 해소했습니다. PM 이슈 제보로 시작해 원인 분석 → 아키텍처
결정 → 배포까지 단독으로 담당했습니다.

## 상세

### 트리거 (원인)
PM 팀으로부터 "상품 목록 페이지가 20초 넘게 로딩된다"는 이슈 접수 (2024-06).
APM 로그 확인 결과 두 가지 원인 발견:
1. `products` 테이블 풀스캔 — 인덱스 없는 `category_id` 필터링
2. 상품별 재고 조회 N+1 쿼리 (상품 100개 → DB 쿼리 101번)

### 아키텍처 결정: Look-aside 패턴 선택 이유
- 상품조회는 **read-heavy** (쓰기 대비 읽기 비율 약 95:5)
- Write-through는 쓰기 시점 캐시 갱신 로직 복잡도 불필요하게 증가
- Look-aside: 캐시 미스 시 DB 조회 후 캐시 적재 — 단순하고 실패 복구 용이
- Cache-aside와 동일 패턴, 팀 내 이미 Redis 인스턴스 운영 중

### 설계 세부
- TTL: 5분 (상품 정보 변경 주기 감안. 재고는 캐시 제외 — 실시간성 필요)
- Eviction: 상품 정보 수정 API 호출 시 해당 키 명시적 삭제(`DEL`)
- 키 구조: `product:list:{category_id}:{page}:{size}`
- 직렬화: Jackson ObjectMapper → JSON string

### 수치 신뢰도 메모 (인터뷰 중 확인)
> 추정: "20초→0.8초" 수치는 이력서에 기재된 값. 인터뷰에서 부하 조건(동시 접속 수,
> 측정 도구, 기준 환경)을 명확히 확인하지 못함. 면접 전 재확인 필요.
> 관찰된 사실: 개발 환경 로컬 테스트 + 간단한 curl 측정 기반 가능성 있음.

### 업데이트 (2026-05-25): 인터뷰 checkpoint 3
- Look-aside 선택 Why 확보 (read-heavy 특성, 쓰기 복잡도 낮음)
- TTL 5분 근거: 상품 정보 평균 변경 주기 검토 결과
- 명시적 eviction 설계 이유: TTL 만료 전 재고 불일치 방지
- 직접 설계 및 구현 여부: 단독 담당 확인 (팀 기존 패턴 아님)
- 수치 측정 방법 불확실 → 추정 마커 유지
