# 상품조회 API 응답 지연 해소 — Redis Look-aside 캐시 도입

## Situation
핀테크 스타트업 A사에서 상품조회 API의 P99 응답시간이 18~20초에 달했습니다.
PM 팀 이슈 제보로 파악했으며, APM 로그 분석 결과 두 가지 원인을 확인했습니다.
첫째, `products` 테이블에 `category_id` 인덱스가 없어 매 요청마다 풀스캔이 발생했습니다.
둘째, 상품별 재고 조회에서 N+1 쿼리 패턴이 발생해(상품 100개 → DB 쿼리 101번)
지연이 누적됐습니다.

## Task
상품조회 API의 응답시간을 사용자가 체감할 수 있는 수준으로 낮추되,
데이터 정합성(특히 재고)을 유지해야 했습니다.
인프라 추가 도입 없이 이미 운영 중인 Redis 인스턴스를 활용하는 것이 제약 조건이었습니다.

## Action
1. **원인 분석**: APM + 직접 쿼리 실행계획 확인으로 풀스캔과 N+1 위치 특정
2. **캐시 패턴 결정**: read-heavy 특성(읽기:쓰기 ≈ 95:5)을 근거로 Look-aside 패턴 채택.
   Write-through는 쓰기 시점 캐시 갱신 로직 복잡도가 불필요하게 증가해 제외.
3. **TTL 설계**: 상품 정보 평균 변경 주기를 감안해 TTL 5분 설정.
   재고 데이터는 실시간성 필요로 캐시 대상에서 제외.
4. **명시적 eviction**: 상품 정보 수정 API 호출 시 해당 캐시 키를 즉시 `DEL`로 삭제.
   TTL 만료 전 데이터 불일치 방지.
5. **키 구조**: `product:list:{category_id}:{page}:{size}` — 페이지네이션 파라미터 포함
6. **배포 및 모니터링**: 스테이징 검증 후 배포. APM으로 캐시 히트율 모니터링.

## Result
> 추정: "20초→0.8초" 수치는 이력서 기재값. 인터뷰에서 부하 조건(동시 접속 수, 측정
> 도구, 기준 환경)을 명확히 확인하지 못했습니다. 개발 환경 로컬 curl 측정 기반일
> 가능성이 있어 프로덕션 수치와 차이가 있을 수 있습니다.

PM 재제보 없음. 체감 응답속도 개선은 팀 내 확인됨.
APM 기준 캐시 히트 시 응답시간 대폭 단축 관찰 (구체 수치는 면접 전 재확인 권장).

## 면접 답변 포인트

이 에피소드를 면접에서 사용할 때 강조할 포인트:

1. **Why Look-aside**: "read-heavy 특성이라 쓰기 복잡도를 낮게 유지할 수 있는
   Look-aside를 선택했습니다. Write-through는 상품 수정 시 캐시 갱신 로직이
   복잡해져 배제했습니다."

2. **TTL vs 명시적 eviction 트레이드오프**: "TTL만 의존하면 5분 동안 stale 데이터를
   서빙할 수 있습니다. 상품 수정 빈도가 낮아서 TTL로 충분하지만, 혹시 즉각 반영이
   필요한 경우를 위해 수정 API에 명시적 DEL도 함께 구현했습니다."

3. **수치에 대한 솔직한 태도**: "측정 수치(20초→0.8초)는 정확한 부하 조건을 다시
   확인할 필요가 있습니다. 당시 개발 환경 기준이었고, 프로덕션 P99는 별도로
   APM에서 확인한 수치로 말씀드리겠습니다."
